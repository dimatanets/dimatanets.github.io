Searching receipts without hitting the table limit

CashAssist Web is HS-Soft’s back-office application for managing cash registers and reviewing sales data. I worked on receipt search in its analytics module, where users find receipts, review their details and export results.

Role
UX designer
Timeline
June 2026
Team
CTO, developer
Tools
Figma, PostHog
Status
Shipped

Context

The CTO asked me to rework receipt search in CashAssist Web’s analytics module. The page could not display a large table, so customers used it very little. When a search failed, developers sent them the data from the system by hand.

Goal

Let people find and export receipts for any period without the page breaking, and make it clear what happens while a long search runs.

Outcome

The redesign shipped with grouped filters, search progress and cancellation, a download option for large results, and receipt details in a drawer.

Reviewing the existing search

I started by reviewing session recordings and heatmaps in PostHog, then walked through the full flow from setting filters to opening a receipt and exporting results.

The review highlighted three areas to address:

  • The long filter form.
  • Missing feedback during searches.
  • Receipt details opening below the results in a second scrollable area.

Three directions, one chosen

I explored three ways to organise receipt search. The first kept the existing layout, with collapsible filter groups and a Calculate button fixed at the bottom. The second reused an established filter pattern already in active use in another HS-Soft product, with main filters above the results and additional filters collapsed by default. The third treated each search as a saved report, with filters shown when creating a new report.

I recommended the first layout for discussion with the team.

Filters that fold away

I grouped the filters into collapsible sections. Applied conditions stay visible as chips above the results, and Reset filters clears them together. The Calculate button stays fixed at the bottom of the filter panel, so it remains available while people scroll through the filters.

A long search people can follow

I designed an empty state for the page before a search starts. While a search runs, the loading state shows how many records have been processed and lets people cancel.

Background search and a notification when results are ready were planned for a later stage.

When the result is too big to show

Results over 50 MB could not be displayed in the table. I designed a state that explains the limit and offers the full results as a file to download.

Opening a receipt

In the original page, clicking a receipt opened its details below the results. This divided the available height between two separately scrollable areas.

I explored three alternatives: a drawer, a split view with a permanent area for receipt details, and an expandable row.

The drawer showed details on demand. The split view kept a dedicated area for checking receipts one after another. An expandable row would push other results down as the receipt grew longer, so I did not consider it suitable for large receipts.

Team review and implementation

I discussed the layouts, search states and receipt views with the CTO and developer. We chose the first layout and the drawer, and I reviewed the implementation as it was built.

The redesign shipped.
