Turning three vibe-coded versions into one loan platform

A loan management platform for an Australian private lender. Over about four weeks I restructured the product, redesigned its main workflows and laid out the structure the team still builds on.

Role
Product designer, sole designer
Team
Product owner, project manager, 3 developers, 1 QA
Timeline
Jul–Aug 2026, about 4 weeks
Tools
Figma, Antigravity, Claude Code
Status
In development

Context

The lender ran its loans in spreadsheets and wanted one platform for applications, servicing and collections. When I joined there were already three working versions: one the client generated with AI, one from our developers and one from our project manager, who has a background in lending systems. Each worked in parts, and none agreed with the others.

Goal

Merge them into one product that an experienced finance person can use without guessing, keep every feature the business relies on, and give developers a structure they can build on.

Outcome

The development team builds on this structure. Applications and loans live on separate screens, a loan page has one row of tabs, and email follow-ups run on rules an admin can edit.

Constraints

Timeline
About a week for the first full version
Context
The client was rarely available, so nobody had the full process written down
Scope
Every real feature had to stay, but some AI-generated ones had no logic behind them
Development
Developers kept building while I designed

Designing in code, reviewing live versions

This was my first product designed mostly in code with AI agents. I started in Antigravity and moved to Claude Code when the number of edits grew. I built the screens with shadcn/ui, the component library the developers already used, and deployed early versions to Vercel. Over five review rounds the product owner, the project manager and the developers clicked through a working product instead of static mockups. Once the direction was agreed, the code moved to the team's repository for development.

Working out what the product actually does

There was no spec, and the process lived in people's heads. Some AI-generated features only looked finished: the product owner couldn't explain tabs like Perfection and Variations, and others were empty placeholders. In the first days I ran a listening tour with the product owner, mapped what each role needs to do and reviewed the existing version against usability heuristics, to separate what the business needs from the noise.

One structure instead of three

Each of the three versions added its own screens, so the product grew sideways. The menu had 51 items in 10 nested sections, applications and active loans shared one pipeline, and a loan had nine tabs with a second row under each one. I flattened the menu to the sections people actually open, split applications and loans into two screens with their own statuses, and grouped the loan page into eight tabs, with sections on one scrolling page and a list on the left.

One place for every message

Messages lived in five places: Email, SMS Center and Bulk Comms in the menu, plus Communications and Correspondence tabs on each loan. I merged them into one Communications section with a single log, and one Communication tab on the loan.

Rules instead of a fixed flow

The team planned to hard-code which documents and emails follow each status change. But nobody, including the client, knew the full process and its edge cases. I proposed automation rules instead: an admin picks a trigger, sets conditions and chooses an action. That let us move on without a complete spec, because changing a rule doesn't need a developer. It also fits the client's plan to offer the platform to partner lenders who work differently.

Hard-coded flow
A status changes, and the system sends a fixed email and asks for fixed documents. Any change to the process needs a new release.
Automation rules
Trigger, conditions, action. An admin edits a rule, saves it disabled, tests it, then turns it on.

Trade-off

I wanted to define which status can follow which before designing the status controls. To ship the MVP on time, the team kept status changes free and used rules only for emails. Transition rules were added later.

Collections as a work queue

Collections needed to support a sequence of actions on an overdue loan: calls, promises to pay and follow-ups. In the earlier version, the action form and history expanded inside each loan row, pushing the rest of the queue down. I moved them into a side panel, keeping the queue visible while a manager reviews a loan or records the next action.

Trade-off

Not every overdue loan should be chased. Some are between people who know each other and get settled in person. So the platform leaves room for judgement: escalation stays a manager's decision, and interest on these loans can be accrued by hand instead of on a schedule.

A design system that had stopped working

The platform shared a design system with two sister products, a share registry and a compliance app. I had built it about four years earlier, before Figma had variables. Its colours were a raw palette with no roles, so screens hard-coded values like gray-600, and new components piled up outside the system. I rebuilt it as two layers of tokens: primitives for colour, spacing and radius, and semantic tokens named by role, such as text-primary, surface or primary button background. I started in Figma, then moved the tokens into code when the AI tools I used turned out to work poorly with Figma.
